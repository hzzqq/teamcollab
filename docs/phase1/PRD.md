# PRD：中型团队任务协作工具 MVP

- 文档版本：v1.0
- 撰写人：产品经理 许清楚（pm）
- 日期：2026-08-05
- 项目性质：从零构建的练手/学习项目，重点探索技术栈与架构设计，不追求商业化

---

## 1. 问题陈述

**谁**：20-100 人中型团队的项目经理（PM）、团队负责人，以及被分配任务的一线执行成员（开发/设计/运营）。

**什么场景**：团队同时推进 3-10 个项目，每个项目 5-30 个任务，需要跨职能协作（产品-设计-开发-测试），负责人要回答"项目什么时候上线、谁在干什么、哪里卡住了"。

**什么痛点**：
1. **重工具用不起也用不动**：Jira、Asana、飞书项目功能全但配置复杂（Jira 首次配置需 2-4 小时/专人管理）、操作慢、按人头收费贵，中型团队没有专职管理员。
2. **轻工具一上规模就崩**：Trello 无任务依赖、无跨项目视图、视图付费墙；Linear 只服务工程团队，跨职能成员（营销/设计）觉得被排斥。
3. **曲线救国越管越乱**：团队用 Notion/多维表格/Excel 自己搭任务表，数据一多就卡（Notion 500 行、多维表格 5 万行性能崩）、无权限体系、无通知、版本混乱，项目经理沦为"表格维护员"。

**现在怎么解决**：靠 Excel 甘特图 + 微信群 + 每日站会口头同步。**为什么不行**：Excel 静态无依赖联动、无实时协作、无责任人视图；微信消息刷屏即丢失上下文；站会只能覆盖当下无法回溯。

**结论**：20-100 人中型团队存在一个明确的"中间地带"空白——**开箱即用、性能不崩、权限清晰、成本可预测**的任务协作工具，既不是 Jira 的卡车，也不是 Trello 的玩具。

### 3.2 替代方案（非专业任务工具如何满足需求）

| 替代方案 | 满足方式 | 关键短板（为何不能长期用） |
|----------|----------|----------------------------|
| Notion 数据库视图 | 用数据库+看板/时间线视图自建任务表 | 无原生任务依赖/关键路径；数据 >500 行性能下降；>10 人实时协作出问题；"万物皆数据库"在 20-50 人时变成维护工程；无权限分级、无通知体系 |
| 飞书多维表格 | 表格+看板+甘特图视图做轻量项目 | 数据量过 5 万行响应肉眼可见变慢；复杂报表要写公式/脚本；安全与审计依赖飞书平台；不是真正的"工作平台"（缺任务通知/负载视图） |
| Excel / 甘特图模板 | 手工绘制甘特图+多人传文件 | 静态、依赖关系手动映射、改一个日期要手动改一串；无实时协作导致版本混乱（v5_final_revised.xlsx）；无资源负载视角、无到期提醒、无权限控制 |

### 3.3 差评洞察 → 市场空白（核心发现）

汇总 7 个直接竞品 + 3 个替代方案的差评，按频次排序的真实痛点：

1. **"要么太重要么太轻"的中间断层**：Jira/飞书项目/Asana 过重（配置复杂、慢、贵），Trello/Linear 过浅（无依赖、无跨项目、只服务单一角色）。**20-100 人中型团队没有"刚刚好"的选项**。
2. **任务依赖与多层级普遍缺失**：Trello/Linear/Notion 均无原生任务依赖；多层级（Epic-任务-子任务）难跟踪，跨项目依赖只能靠脑子记。
3. **跨项目可见性差**：PM 回答"什么时候上线"要翻十个 cycle/看板；Linear/Jira 基础报表都偏浅，中型团队无组合视图。
4. **权限体系两极分化**：Jira 的权限 scheme 复杂到要专人管理；Trello/Notion 几乎没有分级权限。中型团队既想要清晰分级又不想配半天。
5. **成本不可预测**：Asana 25 人逼升企业版、Linear 访客与全价同价、Jira 10 人墙——**只读/访客视角被收全价**是普遍差评点。
6. **多人联合交付无解**：Asana 单 assignee、Trello 无责任人多选——两个人都要 review 的任务只能拆单。
7. **性能崩在数据量上**：Notion 500 行、多维表格 5 万行、Asana 大项目——中型团队数据量恰好踩线。

## 6. MVP 范围

**MVP = 三大能力域（对应 RICE 最高的功能组合）：**

1. **任务管理核心（F1+F2）**：项目/看板 CRUD、任务 CRUD、状态流转（拖拽）、负责人/截止日期/优先级、我的任务视图。
2. **成员协作（F3+F5）**：成员邀请、任务分配、评论、@提及、通知（被分配/被@/到期提醒）。
3. **权限与组织（F4）**：组织-项目两级结构，角色：管理员/成员/只读；项目级成员管理。

**MVP 验收主线**：一个 PM 注册组织 → 邀请 20 人 → 建项目 → 拆任务并分配给 3 个成员 → 成员收到通知 → 成员更新状态 → PM 在我的任务/项目看板看到全局。10 分钟内完成上述全流程（不含注册）。

**进 Backlog（明确不做 MVP）**：任务多层级、任务依赖、列表视图、活动流、跨项目仪表盘、全局搜索、附件、自动化、报表、时间追踪、甘特图。

## 7. 明确不做清单（带原因）

| 不做事项 | 原因 |
|----------|------|
| 文档协作/知识库 | 用户明确不做进 MVP；与 Notion/Confluence 正面竞争且重资产，MVP 聚焦任务闭环。架构上预留"任务 ↔ 文档引用"的数据字段即可 |
| 即时沟通/IM | 用户明确不做；生态已被微信/飞书/钉钉占据，做 IM 无差异化且成本极高。任务评论+@提及已覆盖"围绕任务的沟通" |
| 日程/会议 | 用户明确不做；日历是另一品类。预留任务截止日期→未来日历视图的扩展位 |
| 甘特图/时间线 | 依赖任务依赖（F10）支撑，且实现成本高（拖拽+级联重算）。MVP 用看板+我的任务替代；数据模型预留 start/due 字段 |
| 移动端原生 App | 20-100 人团队以桌面办公为主；MVP 做 Web 响应式，移动端通过浏览器可用。移动端留存作为 P1 埋点观察 |
| 自动化/规则引擎 | Trello Butler 需长期打磨，MVP 阶段成本高收益低。预留 webhook/事件总线设计 |
| 报表/统计图表 | 依赖数据积累；MVP 先埋点（见 §11），数据够了下个迭代再出报表 |
| 时间追踪 | 所有直接竞品普遍缺失或付费墙，属"大家都做不好"的坑，MVP 避开 |
| 附件/文件存储 | 文件存储是重资产（存储/病毒扫描/权限）。MVP 先支持任务挂外链 URL，预留附件表结构 |

## 8. 验收标准（Given/When/Then）

### 8.1 核心任务流
- Given 我是项目管理员且已登录, When 我在项目下创建任务并分配给成员 A、设截止日期, Then 任务出现在项目看板对应列，A 收到"被分配"通知。
- Given 看板上有任务, When 我把它从"进行中"拖到"已完成", Then 状态持久化，其他成员刷新后可见，活动流记录该变更。
- Given 我是被分配人, When 我打开"我的任务"视图, Then 只看到分配给我的任务，逾期任务置顶标红。
- Given 任务有评论, When 我在评论中 @成员 B, Then B 收到通知并可点击直达该任务。

### 8.2 权限
- Given 我是只读成员, When 我尝试编辑任务或删除项目, Then 操作被拒绝并提示无权限（按钮禁用+接口 403）。
- Given 我是管理员, When 我移除某成员的"成员"角色, Then 该成员立即失去编辑权限，但历史任务数据保留。

### 8.3 通知
- Given 任务截止前 24 小时, When 任务仍未完成, Then 负责人收到到期提醒（站内通知）。

## 9. 边界条件

- **空状态**：组织无项目 / 项目无任务 / 我的任务为空时，展示引导文案与"创建第一个任务"入口，不用空洞占位文案。
- **错误状态**：网络失败时任务操作不丢数据（乐观更新+失败回滚+重试提示）；接口错误统一 toast 提示。
- **加载状态**：看板/列表骨架屏；拖拽落位前显示占位槽。
- **边界值**：任务标题 200 字上限；评论 2000 字上限；项目成员上限 100；单看板任务数 >1000 时虚拟滚动。
- **并发**：两人同时编辑同一任务 → 后写覆盖策略 + 变更提示（MVP 采用最后写入优先+活动流记录，不引入冲突合并）。
- **离线**：MVP 不做离线编辑；断网时禁用写操作并提示，读缓存可看。
- **权限拒绝**：非项目成员访问项目 → 404 或"无权限"页，不泄露项目存在性。

## 11. 数据埋点方案（MVP 必埋）

> 不埋 = 上线后无法验证"任务协作"假设是否成立。MVP 阶段重点验证：任务创建转化率、协作深度（评论/分配/通知触达）、留存。

| 事件类别 | 必埋事件 | 说明 |
|----------|----------|------|
| 获客 | page_view, org_created, member_invited | 组织创建与成员邀请转化 |
| 激活 | first_task_created, first_task_assigned | 新成员完成第一个核心操作 |
| 留存 | session_start, session_duration | DAU/MAU、使用频次 |
| 协作 | task_comment_created, task_mention_sent, task_status_changed | 协作深度信号 |
| 转化/预警 | task_due_soon, task_overdue | 逾期率、到期提醒触达 |
| 异常 | error_occurred | 前端错误 + API 错误 |

**埋点实现要求**
- 前端用轻量 SDK 或自建 `trackEvent()` 封装，事件命名 `{对象}_{动作}`（如 `task_created`, `task_status_changed`）。
- 属性：每个事件附带 `user_id`, `timestamp`, `device`, `version`。
- 不采集隐私数据（不上报 IP、不存原始输入内容）。
